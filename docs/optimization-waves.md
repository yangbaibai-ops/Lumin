## 波次 2（2026-10-05）：性能 —— 先把报告的两个数字**用自己的探针复测**，再决定砍哪儿

### 2.1 结论先说：报告的两个性能数字**一个是陈旧的、一个是真问题**

| 报告主张（§4.2 / §7.4）                          | 复测结果                                                                                                                                                                                    | 判定                                                                                                                                                                                                  |
| ------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 「2000 个代码围栏的 56 KB 文档装载 **52–62 s**」 | `tools/_probe-fences-total.js`（2000 围栏 / 57,779 字符 textarea）：**load+flush 756ms，切源码 578ms，切回 116ms，全程 1450ms**                                                             | **陈旧** —— 代码块 CM 虚拟化（F 项）已把它解决：块只在视口附近挂 CM，实测 500 围栏时 CM 实例峰值 **10 个**（虚拟化前 500 个），`_verify-cb-virtualization` 18/18 守着"按需挂载 / 高度稳定 / 选区保护" |

### 2.2 为什么旧阈值没拦住：它量错了口径

`lib/largeDoc.ts` 的降级闸（超阈值直接进源码模式）此前是 `HEAVY_FENCES=800` / `HEAVY_CHARS=1M`。
1M 这个数是照旧审计那句"572,262 字符 → 打开 **2.24s**"定的 —— 而那句话量的是 `openPath` 返回，
**用户真正能用的时刻是 DOM 稳定**。两者差 2–3 倍，于是 373k / 420k 字符的散文（977 KB / 1.1 MB 文件）
从闸下面漏了过去，代价是 6–9 秒不可用 + 1.2 GB 常驻 —— 正是报告里"打开一篇长文吃掉 1.4GB"那条。

CPU 采样（同一探针 `LUMIN_PROBE_PROFILE=1`，6930ms 采样）说明这 4.4 秒**不是我们的代码**：
markdown-it `ParserBlock.tokenize` 717ms、prosemirror-markdown `atBlank` 1168ms、
PM 内部（`nodesBetween`/`nodeSize`/`isLeaf`）约 490ms、GC 411ms、我们自己的滚动恢复
`applyScrollRatio` 356ms，其余零散 ⇒ 这是第三方解析 + PM 建 DOM 的常数，一次改动消不掉。

### 2.3 这一波做了什么

**重新标定降级闸**（`HEAVY_CHARS` 1M → **300k**，围栏仍 800）：

- 依据：实测总耗时 ≈ **17 µs/字符**（open 5.3 + render 11.7）⇒ 5 秒线 ≈ 290k 字符，取整 300k；
  同时把"降级原因"做成纯函数 `heavyReason()`（`fences` / `chars`），提示文案说对是哪一种
  （一份 977 KB 的纯散文没几个代码块，说"有 0 个代码块"只会让人困惑）。
- 复测（同探针、同一 977 KB 文档）：

|                             | 改前              | 改后                                     |
| --------------------------- | ----------------- | ---------------------------------------- |
| 入口模式                    | 渲染面（WYSIWYG） | **源码面**（并给出原因提示，可一键切回） |
| `open`                      | 1965–2173 ms      | **454 ms**                               |
| 默认可用（open + 入口就绪） | **6340 ms**       | **454 ms**                               |
| 入口常驻内存                | 1272 MB           | **604 MB**                               |
| DOM 元素 / 布局对象         | 30,939 / 151,977  | **97 / 169**                             |
| 报告验收线（977 KB ≤5s）    | FAIL（6.34s）     | **PASS（0.45s）**                        |
| 1.1 MB 那一档               | 8.59s / 1247MB    | **0.53s / 624MB**                        |

- **诚实标注代价**：用户若坚持切回渲染面，代价仍在（977 KB → +3.4s / ~1.2GB；1.1 MB → +4.2s）。
  彻底解决它需要**段落级虚拟化**（PM 目前整篇建 DOM），那是另一个量级的工程；
  这一波选择了与代码围栏同一套机制（降级 + 明确告知 + 可切回），把默认路径拉回秒级。
- 新增可复跑探针 `tools/_probe-bigprose.js`（与 `_probe-cb-scale` / `_probe-fences-total` 同一入口）：
  `node tools/run-suites.js --suite=_probe-bigprose.js`，`LUMIN_PROBE_BYTES=977000,1100000`、
  `LUMIN_PROBE_PROFILE=1`（采样归因）、`LUMIN_PROBE_SWITCH=1`（量"硬要切渲染面"的代价）。
- 单测：`tests/largeDoc.test.mjs` 6 → **8 条**（阈值钉住、降级原因可区分、"20 万字中文长篇要闸住"）。
- 回归：`_verify-surface-stress` **72/72**（含 1MB 与 2000 围栏两档）、`_verify-cb-virtualization` 18/18、
  `_verify-open-in-new-window` 3/3；单测 **749/749**。

### 2.4 顺手修掉波次 1 引入的一处竞态（全量矩阵抓出来的）

全量矩阵第一遍 **20/21**：红的是 `_verify-md-fidelity.js` 的"历史 关闭后不再写快照"（`entries=2`），
而且**间歇**（单独重跑 3 次：1 次 FLAKY 转绿、1 次红、1 次红）。查下来是波次 1 的
`settings:changed` 回播引入的竞态：

1. 渲染层 `set('historyEnabled', false)`（进 250ms 节流落库队列）；
2. **上一次落库的回播**此刻到达 —— 它的快照取自更早，该键还是 `true`；
3. `applyRemote()` 整份 `$patch` ⇒ 刚改的那条被打回，随后的落库把 `true` 写回 kv；
4. 主进程 `recordHistoryBeforeOverwrite` 读到 `true` ⇒ 明明关了历史，快照照写。

**修法**：`writeSettings(next, { broadcast })` —— **渲染层发起**的写入只落库不回播
（它本来就有这份状态），只有**主进程侧**的改动（原生菜单主题、备份目录）才广播 ——
那才是回播存在的理由。没有改成"增量落库"，是因为那要动落库协议与 diff 逻辑，
而这条路径的语义本来就应该是"主进程侧改动才通知渲染层"。

**验收**：`_verify-md-fidelity` 连跑 3 次 **PASS / 0 FLAKY**；`_verify-backup` 新增
「主进程侧写设置 → 渲染层 store 被动同步」（渲染层先放假值 → 调 `useDefaultDir()` → 断言被改回
`null`）→ **19/19**；`_verify-md-fidelity` 补了一条前置断言「关闭设置真的落库了」，
以后同类问题一眼分清是"设置没到"还是"历史没关"。
